# План разработки frontend (TDD)

## 1. Цель frontend части

Frontend должен предоставить два удобных интерфейса для работы с системой заказов еды:

- клиентский интерфейс для просмотра меню, корзины и оформления заказа;
- административный интерфейс для управления меню и обработки заказов.

Frontend должен быть:

- модульным;
- понятным по структуре;
- подготовленным к масштабированию;
- покрытым тестами на ключевые пользовательские сценарии;
- независимым от будущего мобильного приложения, то есть не содержать бизнес-логику, которая должна находиться на backend.

Разработка frontend ведется по **TDD-подходу**: сначала определяем поведение экранов и компонентов через тесты, затем реализуем минимальный код, затем выполняем рефакторинг.

## 2. Подход к frontend-разработке по TDD

Основной цикл разработки каждой функции:

1. определить пользовательский сценарий;
2. определить состояние интерфейса и поведение;
3. написать тест;
4. убедиться, что тест падает;
5. реализовать минимальный код;
6. добиться прохождения теста;
7. выполнить рефакторинг;
8. добавить тесты на ошибки, загрузку и крайние случаи.

Для frontend TDD особенно важно тестировать не внутреннюю реализацию, а поведение:

- что видит пользователь;
- что происходит при клике;
- как экран реагирует на загрузку;
- как отображаются ошибки;
- как меняется интерфейс в зависимости от роли.

## 3. Основная стратегия frontend

### 3.1. Общий принцип

Frontend не должен быть просто набором страниц.
Он должен быть организован вокруг пользовательских сценариев:

- вход в систему;
- просмотр меню;
- управление меню;
- оформление заказа;
- обработка заказов в админке.

### 3.2. Архитектурные принципы

- бизнес-правила хранятся на backend, а frontend отвечает за отображение и взаимодействие;
- экраны делятся на клиентские и административные;
- доступ к экранам зависит от роли пользователя;
- общие UI-элементы и инфраструктура выносятся в общие модули;
- работа с API централизуется;
- ошибки, загрузки и пустые состояния закладываются сразу.

### 3.3. Рекомендуемый стек

- `React + TypeScript`;
- `Vite`;
- `React Router`;
- `React Query` или аналог для загрузки серверного состояния;
- `Axios` или `fetch`-обертка;
- `Jest` или `Vitest`;
- `React Testing Library`.

Если проект будет активно расти, желательно сразу использовать:

- feature-based структуру папок;
- единый UI-kit или хотя бы слой базовых компонентов;
- отдельный модуль для auth-state.

## 4. Рекомендуемая структура проекта

```text
src/
  app/
    providers/
    router/
    layouts/
  pages/
    auth/
    admin/
    client/
  features/
    auth/
    users/
    categories/
    products/
    cart/
    orders/
  entities/
    user/
    product/
    category/
    order/
  shared/
    api/
    ui/
    lib/
    hooks/
    constants/
    types/
    utils/
  tests/
```

Такой подход поможет:

- не смешивать бизнес-функции;
- удобно развивать админку и клиентскую часть параллельно;
- проще писать тесты на отдельные фичи.

## 5. Стратегия тестирования frontend

### 5.1. Unit tests

Используются для:

- утилит;
- форматтеров;
- функций преобразования данных;
- простых хуков;
- role-based helper-функций;
- функций работы с токеном.

### 5.2. Component tests

Это основной слой тестирования frontend.

Покрывают:

- формы;
- таблицы;
- карточки товара;
- корзину;
- фильтры;
- состояние загрузки;
- ошибки;
- ролевое отображение UI.

### 5.3. Integration tests

Покрывают:

- сценарий логина;
- защищенные роуты;
- работу страницы со state management и API mock;
- взаимодействие нескольких компонентов на экране.

### 5.4. E2E tests

Желательны хотя бы для ключевых сценариев:

- login;
- создание заказа;
- просмотр списка заказов;
- смена статуса заказа в админке.

Если E2E не будут добавлены сразу, их можно включить после появления стабильного MVP.

## 6. Что тестировать в первую очередь

На старте нужно покрыть сценарии, которые дают максимальную ценность:

1. login и защита роутов;
2. загрузка и отображение меню;
3. корзина и оформление заказа;
4. список заказов в админке;
5. ограничения UI по ролям.

## 7. Порядок frontend-разработки по TDD

### Этап 0. Каркас frontend и тестовая инфраструктура

**Оценка:** 2-3 дня

#### Что сделать

- создать проект на `React + TypeScript`;
- настроить `Vite`;
- подключить роутинг;
- подключить тестовую среду;
- настроить `React Testing Library`;
- настроить базовые providers;
- настроить слой API;
- подготовить общую структуру папок;
- подготовить базовый layout.

#### Сначала написать тесты на

- базовый рендер приложения;
- работу роутера;
- отображение страницы 404;
- базовый защищенный маршрут.

#### Результат этапа

Есть структурированный frontend-проект и готовая тестовая среда.

---

### Этап 1. Auth и защищенные маршруты

**Оценка:** 3-4 дня

#### Сначала описать тестами

- форма логина отображается корректно;
- пользователь может ввести логин и пароль;
- при успешном ответе токен сохраняется;
- после логина происходит переход в защищенную область;
- без токена защищенный маршрут недоступен;
- при ошибке логина отображается сообщение.

#### После тестов реализовать

- страницу логина;
- auth state;
- storage токена;
- private routes;
- logout;
- базовый layout после входа.

#### Что важно покрыть

- загрузку формы;
- ошибку авторизации;
- успешный редирект;
- восстановление сессии после перезагрузки страницы.

#### Результат этапа

Пользователь может войти в систему и попасть в доступную ему часть приложения.

---

### Этап 2. Базовая структура админки

**Оценка:** 2-3 дня

#### Сначала описать тестами

- layout админки корректно рендерит меню;
- активный маршрут подсвечивается;
- недоступные разделы скрываются по роли;
- unauthorized пользователь не видит запрещенные разделы.

#### После тестов реализовать

- sidebar или верхнюю навигацию;
- layout админки;
- базовый dashboard-заглушку;
- структуру роутов админской части.

#### Результат этапа

Есть каркас админки, в который можно безопасно добавлять рабочие разделы.

---

### Этап 3. Категории и продукты в админке

**Оценка:** 4-6 дней

#### Сначала описать тестами

- список продуктов отображается после успешной загрузки;
- отображается состояние загрузки;
- отображается состояние ошибки;
- форма создания продукта валидируется;
- продукт можно создать;
- продукт можно отредактировать;
- продукт можно удалить;
- пользователь без нужной роли не видит кнопки управления.

#### После тестов реализовать

- страницу списка продуктов;
- страницу или модальное окно создания/редактирования продукта;
- список категорий;
- создание и редактирование категорий;
- валидацию форм;
- обработку API ошибок.

#### На что обратить внимание

- если данных нет, должен быть корректный empty-state;
- действия удаления должны иметь подтверждение;
- роли должны влиять не только на маршрут, но и на UI-кнопки.

#### Результат этапа

Админка позволяет управлять меню.

---

### Этап 4. Клиентская часть: меню и корзина

**Оценка:** 4-5 дней

#### Сначала описать тестами

- клиент видит список категорий и продуктов;
- продукт можно добавить в корзину;
- количество позиции можно изменить;
- позицию можно удалить из корзины;
- итоговая сумма пересчитывается корректно;
- пустая корзина отображается корректно.

#### После тестов реализовать

- страницу меню;
- карточки продуктов;
- состояние корзины;
- добавление и удаление товаров;
- обновление количества;
- отображение итогов.

#### Unit tests

- пересчет суммы;
- работа cart helper-функций;
- преобразование структуры данных корзины.

#### Результат этапа

Клиент может собрать заказ и подготовиться к оформлению.

---

### Этап 5. Оформление заказа

**Оценка:** 2-4 дня

#### Сначала описать тестами

- пользователь может отправить валидный заказ;
- кнопка отправки блокируется при пустой корзине;
- при успешном заказе корзина очищается;
- при ошибке заказа отображается сообщение;
- пользователь видит подтверждение отправки.

#### После тестов реализовать

- экран оформления заказа;
- интеграцию с `POST /orders`;
- success state;
- error state;
- очистку корзины после успешной отправки.

#### Результат этапа

Клиент может завершить основной сценарий и оформить заказ.

---

### Этап 6. Заказы в админке

**Оценка:** 3-5 дней

#### Сначала описать тестами

- список заказов загружается и отображается;
- администратор видит статус каждого заказа;
- статус можно изменить;
- ошибка обновления статуса отображается;
- недоступные действия скрыты для роли без прав.

#### После тестов реализовать

- страницу заказов;
- таблицу или список заказов;
- просмотр деталей заказа;
- смену статуса;
- фильтрацию по статусу на базовом уровне.

#### Важно покрыть

- повторную загрузку;
- обновление UI после смены статуса;
- поведение при пустом списке заказов.

#### Результат этапа

Админка поддерживает основной операционный процесс обработки заказов.

---

### Этап 7. История заказов клиента

**Оценка:** 2-3 дня

#### Сначала описать тестами

- пользователь видит только свои заказы;
- список заказов корректно отображается;
- отображается статус заказа;
- при отсутствии заказов показывается пустое состояние.

#### После тестов реализовать

- страницу истории заказов;
- список заказов клиента;
- детализацию заказа при необходимости.

#### Результат этапа

Клиент может отслеживать свои заказы после оформления.

---

### Этап 8. Финализация UX и стабилизация

**Оценка:** 2-4 дня

#### Сначала описать тестами

- ошибки API корректно отображаются;
- экраны ведут себя корректно при загрузке;
- пустые состояния рендерятся во всех ключевых разделах;
- запрещенные элементы скрыты по роли.

#### После тестов реализовать

- единый подход к уведомлениям;
- skeleton/loading states;
- error boundaries при необходимости;
- улучшение навигации;
- доработка доступности интерфейса.

#### Результат этапа

Frontend становится пригодным для демонстрации и использования первым клиентом.

### Admin UI

- скрытие разделов по роли;
- отображение списка продуктов;
- создание продукта;
- редактирование продукта;
- удаление продукта;
- отображение списка заказов;
- смена статуса заказа.

### Client UI

- отображение меню;
- добавление товара в корзину;
- изменение количества;
- удаление товара;
- отправка заказа;
- очистка корзины после успешного заказа;
- отображение истории заказов.

### Shared behavior

- загрузка;

- empty-state;
- маршрутизация;

## 9. Рекомендуемый порядок написания кода внутри frontend-фичи

Для каждой фичи удобно использовать следующий порядок:

1. описать пользовательский сценарий;
2. выделить компоненты и состояние;
3. написать тесты на поведение;
4. реализовать контейнер или страницу;
5. реализовать UI-компоненты;
6. подключить API;
7. обработать loading, error и empty-state;
8. выполнить рефакторинг.

## 10. Что важно не упустить при frontend TDD

### 10.1. Тестировать поведение, а не внутренние детали

Нужно проверять:

- что пользователь видит;
- что пользователь может нажать;
- как интерфейс реагирует на действия;
- как отображаются ошибки и загрузка.

Не стоит сильно завязываться на:

- внутренний state конкретного компонента;
- приватные реализации хуков;
- детали реализации, которые можно безопасно менять при рефакторинге.

### 10.2. Роли нужно проверять не только в роутинге

Права доступа на frontend должны влиять и на:

- видимость меню;
- кнопки действий;
- доступность форм;
- отображение отдельных экранов.

### 10.3. Не переносить бизнес-логику с backend на frontend

Frontend может:

- валидировать форму;
- помогать пользователю;
- показывать удобный интерфейс.

Но frontend не должен быть источником истины для:

- ролей;
- tenant-изоляции;
- итоговых прав доступа;
- допустимых бизнес-операций.

## 11. Подготовка frontend к мобильному приложению

Так как мобильное приложение планируется в будущем, уже сейчас важно:

- не связывать backend-контракты с конкретной версткой;
- использовать чистые API-модели;
- минимизировать дублирование бизнес-логики на клиенте;
- сохранять четкую структуру фичей и сущностей;
- документировать пользовательские сценарии и API-ожидания.

## 13. Вывод

Frontend для этого проекта нужно строить как набор понятных пользовательских сценариев, а не просто как страницы.

Оптимальный путь:

- сначала структура проекта и тестовая среда;
- потом auth и защищенные маршруты;
- затем админка;
- затем клиентское меню, корзина и заказ;
- после этого стабилизация UX.

Подход через TDD позволит рано зафиксировать поведение интерфейса, уменьшить число регрессий и ускорить развитие продукта после запуска MVP.
