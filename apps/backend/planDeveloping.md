# План разработки backend (TDD)

## 1. Цель backend части

Backend должен стать единым надежным API для SaaS-приложения заказов еды.

Он должен решать следующие задачи:

- аутентификация и авторизация пользователей;
- изоляция данных по tenant;
- управление меню;
- прием и обработка заказов;
- предоставление API для веб-клиента, админки и будущего мобильного приложения.

Разработка backend ведется по подходу **TDD**: сначала описывается структура и поведение через тесты, затем пишется минимальная реализация, затем код рефакторится.

## 2. Подход к разработке: TDD

Основной цикл работы по каждой функции:

1. определить контракт и поведение;
2. написать тест;
3. запустить тест и убедиться, что он падает;
4. написать минимальный код, чтобы тест прошел;
5. выполнить рефакторинг;
6. добавить дополнительные тесты на ошибки и крайние сценарии.

Это нужно, чтобы:

- рано фиксировать бизнес-правила;
- не размывать архитектуру;
- безопасно развивать multi-tenant логику;
- упростить будущую поддержку и подключение мобильного клиента.

## 3. Общая архитектурная стратегия backend

### 3.1. Основные требования

Backend должен быть:

- модульным;
- предсказуемым по контрактам;
- покрытым тестами на критичные сценарии;
- готовым к multi-tenant;
- независимым от конкретного frontend.

### 3.2. Рекомендуемая структура проекта

```text
src/
  main.ts
  app.module.ts
  config/
  common/
    guards/
    decorators/
    filters/
    interceptors/
    dto/
    types/
    constants/
  database/
  auth/
    auth.module.ts
    auth.controller.ts
    auth.service.ts
    jwt.strategy.ts
    guards/
    dto/
    tests/
  users/
    users.module.ts
    users.controller.ts
    users.service.ts
    dto/
    tests/
  tenants/
    tenants.module.ts
    tenants.service.ts
    tests/
  categories/
  products/
  orders/
  health/
test/
  integration/
  e2e/
```

### 3.3. Архитектурные принципы

- бизнес-логика должна жить в сервисах;
- контроллеры должны быть тонкими;
- DTO используются для входных данных;
- вся проверка ролей и tenant выполняется на backend;
- каждый модуль тестируется отдельно;
- общие механизмы выносятся в `common/`.

## 4. Стратегия тестирования

TDD будет эффективным только если заранее разделить тесты по уровням.

### 4.1. Unit tests

Покрывают:

- сервисы;
- бизнес-правила;
- статусы заказов;
- проверки ролей;
- проверки tenant-логики;
- вспомогательные функции и policy-слой.

Цель:

- максимально быстро проверять логику без БД и HTTP.

### 4.2. Integration tests

Покрывают:

- работу сервисов с БД;
- ORM и репозитории;
- реальные запросы к сущностям;
- корректность tenant-фильтрации;
- работу модулей в связке.

Цель:

- убедиться, что код реально работает с базой и не ломается на уровне persistence.

### 4.3. E2E tests

Покрывают:

- login;
- создание заказа;
- просмотр заказов;
- смену статуса заказа;
- запрет доступа при неверной роли;
- запрет доступа к чужому tenant.

Цель:

- проверить реальные пользовательские сценарии через HTTP API.

### 4.4. Язык тестовых кейсов

- все названия тестов (`describe`, `it`) обязательно писать на кириллице;
- формулировки тестов должны описывать поведение понятным русским языком;
- англоязычные названия допускаются только для технических терминов API/протоколов (`JWT`, `HTTP`, `DTO`).

## 5. Что тестировать в первую очередь

Самые критичные зоны backend:

1. аутентификация;
2. роли и доступы;
3. multi-tenant изоляция;
4. создание заказа;
5. переходы статусов заказа.

Если тестов мало, начинать нужно именно с этих зон.

## 5.1. Уточненные требования к пользователям и ролям

Ниже зафиксированы продуктовые правила перед началом Этапа 1.

### Регистрация клиента (`user`)

- пользователь-клиент регистрируется самостоятельно;
- перед завершением регистрации пользователь обязан согласиться с политикой конфиденциальности;
- в MVP-форме регистрации обязательны 2 поля:
  - `phone` (только российский номер);
  - `firstName`.

### Ролевая модель и права создания пользователей

Используемые роли:

- `superAdmin`
- `admin`
- `moderator`
- `operator`
- `user` (клиент приложения)

Правила создания пользователей через админку:

- `operator` и `moderator` может создать только `admin` или `superAdmin`;
- `admin` может создать только `superAdmin`;
- роль `superAdmin` не создается обычными админскими операциями (задается вручную/seed/закрытым процессом);
- роль `user` создается через публичную регистрацию клиента.

### Единая таблица пользователей

Все пользователи хранятся в одной таблице `users`.

Поля таблицы:

- `id` — уникальный идентификатор;
- `tenantId` — опционально, ссылка на организацию (`tenants.id`);
- `email` — опционально;
- `phone` — обязательно, только РФ формат;
- `role` — роль пользователя (`superAdmin | admin | moderator | operator | user`);
- `firstName` — обязательно;
- `lastName` — опционально;
- `isActive` — boolean;
- `createdAt`, `updatedAt`.

### Уточнение по SaaS-модели организаций

Новый продуктовый контекст требует скорректировать трактовку tenant-модели.

Важно:

- в системе будет список организаций;
- у каждой организации своя инфраструктура данных:
  - категории
  - продукты
  - цены
  - заказы
- пользователь-клиент должен видеть список организаций и иметь возможность сделать заказ в каждой из них;
- staff-пользователи (`admin`, `moderator`, `operator`) по-прежнему относятся к конкретной организации;
- `superAdmin` работает над платформой в целом и не привязан к одной организации.

Из этого следует важное архитектурное правило:

- поле `tenantId` у `users` нельзя трактовать одинаково для всех ролей;
- для staff-пользователей связь с tenant остается прямой и обязательной по бизнес-смыслу;
- для клиентского пользователя `user` нельзя жестко фиксировать единственный tenant как постоянную принадлежность ко всей системе;
- принадлежность клиента к организации должна определяться не самим пользователем как сущностью платформы, а его действиями в контексте конкретной организации:
  - просмотр меню tenant
  - создание заказа tenant
  - история заказов по tenant

Практический вывод для следующего шага:

- `tenantId` у `User` должен рассматриваться как staff-ориентированная связь;
- tenant-контекст для клиента должен входить в заказы и публичные каталоги организаций;
- заказы клиента должны быть привязаны к организации (`tenant`), а не вся клиентская учетная запись целиком к одной организации.

### Валидации для Этапа 1

- `phone` валидируется как российский номер (например, E.164 для РФ: `+79XXXXXXXXX`);
- поле согласия с политикой конфиденциальности обязательно для регистрации `user`;
- для ролей в админке проверяется и целевая роль, и роль инициатора создания.

### Этап 2.1. Ревизия tenant-модели для списка организаций

**Оценка:** 2-4 дня

После уточнения продуктового сценария этот этап становится обязательным перед полноценной реализацией категорий, продуктов и заказов.

#### Что нужно зафиксировать архитектурно

- платформа хранит список организаций;
- каждая организация является отдельным tenant;
- staff-пользователь принадлежит одной организации;
- клиентский пользователь может работать с несколькими организациями;
- меню, категории, продукты, цены и заказы всегда существуют в контексте конкретной организации;
- нельзя смешивать данные разных организаций в одном заказе.

#### Сначала описать тестами

- публичный список организаций возвращается корректно;
- клиент может запросить каталог конкретной организации;
- staff пользователя tenant A нельзя использовать для управления tenant B;
- заказ нельзя создать из продуктов разных организаций;
- заказ нельзя создать с категорией/продуктом чужого tenant;
- пользователь может иметь заказы в нескольких организациях;
- история заказов корректно фильтруется по организации;
- клиентский пользователь не получает глобальную привязку только к одному tenant без бизнес-основания.

#### После тестов реализовать

- четкую модель `tenants` как списка организаций;
- публичный endpoint списка организаций;
- tenant-aware доступ к меню организации;
- tenant-aware доступ к ценам;
- tenant-aware модель заказа;
- явную стратегию различия:
  - `staff -> tenant-bound`
  - `client user -> platform user with tenant-scoped orders`

#### Результат этапа

Backend перестает быть моделью "один пользователь -> один tenant" для всех ролей и становится корректной SaaS-платформой со списком организаций и tenant-aware заказами.

### Этап 3. Модуль ролей и доступов

**Оценка:** 1-2 дня

Хотя базовые роли появятся вместе с auth, полный контроль доступа лучше выделить отдельно.

#### Сначала описать тестами

- `admin` имеет полный доступ;
- `moderator` имеет доступ только к разрешенным endpoint;
- `operator` не может управлять меню;
- доступ запрещается при отсутствии нужной роли.

#### После тестов реализовать

- `RolesGuard`;
- декоратор ролей;
- матрицу доступа по endpoint;
- единый подход к ответу `403 Forbidden`.

#### Результат этапа

Права доступа становятся централизованными и предсказуемыми.

#### Что уже выполнено частично

- добавлен декоратор `Roles`;
- добавлен `RolesGuard`;
- зафиксированы роли:
  - `superAdmin`
  - `admin`
  - `moderator`
  - `operator`
  - `user`
- реализован отдельный админский сценарий создания staff-пользователей:
  - `POST /users/staff`
- добавлен `UsersManagementService` с правилами создания ролей через админку;
- уже реализованы бизнес-ограничения:
  - `admin` и `superAdmin` могут создавать `operator` и `moderator`;
  - только `superAdmin` может создавать `admin`;
  - роль `user` нельзя создавать через админку;
  - роль `superAdmin` нельзя создавать через админку;
  - запрещено создание пользователя с дублирующимся телефоном.

#### Что добавлено для админки

Для административной части backend уже подготовлена основа управления пользователями:

- endpoint `POST /users/staff` для создания сотрудников;
- role-based защита endpoint;
- DTO для создания staff-пользователя;
- сервис бизнес-логики для проверки прав создания ролей;
- unit-тесты на правила создания пользователей из админки;
- e2e-тесты на ключевые сценарии создания staff-пользователей.

Что уже покрыто e2e для админки:

- запрет создания staff-пользователя без токена;
- запрет создания staff-пользователя пользователем с ролью `user`;
- запрет создания staff-пользователя пользователем с ролью `moderator`;
- успешное создание `operator` пользователем `admin`;
- запрет создания `admin` пользователем `admin`;
- успешное создание `admin` пользователем `superAdmin`.

### Этап 6. Заказы

**Оценка:** 5-7 дней

Это главный бизнес-модуль, поэтому здесь особенно важно строго придерживаться TDD.

#### Сначала описать тестами

- клиент может создать заказ;
- заказ нельзя создать с пустым составом;
- заказ нельзя создать с продуктом другого tenant;
- пользователь может видеть только свои заказы;
- админ/оператор может видеть список заказов tenant;
- статус можно менять только по допустимому сценарию;
- нельзя изменить заказ другого tenant;
- нельзя выполнить запрещенный переход статуса.

#### После тестов реализовать

- модуль `orders`;
- `orders` и `order_items`;
- endpoint создания заказа;
- endpoint списка заказов клиента;
- endpoint списка заказов для админки;
- endpoint смены статуса;
- проверки статусов и прав доступа.

#### Рекомендуемая минимальная модель статусов

- `new`
- `confirmed`
- `done`
- `cancelled`

#### Обязательные unit tests

- проверка валидности статусов;
- правила переходов;
- расчет итоговых данных заказа;
- валидация состава заказа.

#### Обязательные integration / e2e tests

- создание заказа через API;
- получение списка своих заказов;
- получение заказов админом;
- смена статуса;
- отказ при нарушении tenant или роли.

#### Результат этапа

Работает основной бизнес-процесс заказа.

### Этап 7. Стабилизация и техническое усиление

**Оценка:** 2-3 дня

#### Что покрыть тестами

- ошибки валидации DTO;
- глобальные exception filters;
- edge-cases по доступам;
- пустые списки;
- несуществующие id;
- частые пользовательские ошибки.

#### Что доработать

- единый формат ошибок;
- логирование;
- health-check;
- swagger-документация;
- базовые ограничения безопасности.

#### Результат этапа

Backend становится пригодным для первого production-запуска.

### Этап 7.1. Security hardening backend

**Оценка:** 2-4 дня

Этот этап становится следующим обязательным шагом параллельно развитию multi-tenant модели.

#### Что проверить в первую очередь

- устойчивость auth и registration к вредоносному вводу;
- устойчивость DTO и сервисов к script injection payload;
- устойчивость слоя доступа к данным к SQL injection;
- корректность authorization по ролям;
- корректность tenant-изоляции при доступе к данным;
- отсутствие небезопасных raw SQL вызовов без параметризации;
- устойчивость публичных endpoint к brute force и бот-активности.

#### Ключевые риски

- script injection через названия организаций, категорий, продуктов или профильные поля;
- SQL injection через raw query или небезопасную динамическую фильтрацию;
- обход authorization через неправильную проверку роли или tenant;
- массовые запросы на `register` и `login`;
- утечка данных между организациями;
- доверие только frontend-валидации без жесткой backend-проверки.

#### Сначала описать тестами

- вредоносные строки в DTO не ломают обработку и не обходят валидацию;
- SQL injection payload не влияет на выборку данных;
- запрос без нужной роли получает отказ;
- запрос с tenant A не может получить данные tenant B;
- login не выдает лишней информации о существовании пользователя;
- registration корректно обрабатывает повторные и вредоносные запросы;
- protected endpoint недоступен без валидного токена;
- raw SQL, если появится, используется только параметризованно.

#### После тестов реализовать

- review всех публичных auth endpoint;
- review всех мест с динамическими фильтрами и будущими raw query;
- защиту от script injection на уровне DTO/сервисов/хранимых данных;
- rate limiting для публичных auth endpoint;
- anti-bruteforce подход для `login`;
- централизованный security checklist для новых модулей;
- подготовку точки интеграции для captcha в будущем.

#### Что добавить позже

- captcha для `register`;
- captcha или adaptive challenge для `login`;
- audit log для auth-событий;
- расширенные security e2e сценарии;
- review refresh/session стратегии, если auth-схема будет расширяться.

#### Результат этапа

Backend становится существенно устойчивее к script injection, SQL injection, ошибкам authorization и массовым злоупотреблениям публичными auth endpoint.

## 7. Минимальный список тестов для MVP

Ниже обязательный минимальный набор тестов, который должен быть в MVP:

### Auth

- успешный login;
- неуспешный login;
- доступ к защищенному endpoint с токеном;
- отказ без токена.

### Roles

- доступ admin к защищенному endpoint;
- отказ operator в endpoint управления меню;
- корректная работа `RolesGuard`.

### Multi-tenant

- пользователь tenant A не видит данные tenant B;
- нельзя обновлять сущности чужого tenant;
- новые сущности создаются с tenant текущего пользователя.
- публичный список организаций возвращается корректно;
- заказ нельзя собрать из продуктов разных организаций.

### Products / Categories

- CRUD категории;
- CRUD продукта;
- tenant-изоляция;
- role-based restrictions.

### Orders

- создание валидного заказа;
- отказ при пустом заказе;
- просмотр своих заказов;
- просмотр заказов админкой;
- смена статуса;
- отказ при некорректном переходе статуса.

### Security

- вредоносные строки не обходят DTO-валидацию;
- SQL injection payload не меняет результат выборки;
- protected endpoint недоступен без токена;
- protected endpoint недоступен при неверной роли;
- tenant B не может получить данные tenant A;
- login не раскрывает лишние детали злоумышленнику.

## 8. Рекомендуемый порядок написания кода внутри каждого модуля

Для каждого backend-модуля лучше придерживаться такого порядка:

1. описать use-cases;
2. определить DTO и контракты;
3. написать unit tests на сервис;
4. написать integration tests для работы с БД;
5. реализовать сервис;
6. реализовать controller;
7. написать или обновить e2e tests;
8. выполнить рефакторинг.

## 9. Что важно не упустить при TDD

### 9.1. Не тестировать framework вместо логики

Не нужно тратить много времени на тесты очевидного поведения NestJS.
Нужно тестировать именно свою бизнес-логику:

- кто что может делать;
- какие данные видит пользователь;
- какие статусы допустимы;
- что запрещено между tenant.

### 9.2. Не писать слишком много хрупких тестов на внутреннюю реализацию

Лучше проверять:

- поведение;
- входные данные;
- итоговый результат;
- побочные эффекты в БД.

И хуже проверять:

- сколько раз вызван приватный метод;
- внутреннюю структуру сервиса без бизнес-смысла.

### 9.3. Multi-tenant должен проверяться почти в каждом модуле

Для этого проекта `tenant_id` — это не частная деталь, а фундамент архитектуры.
Поэтому тесты tenant-изоляции должны присутствовать во всех ключевых модулях.

### 9.4. Security нужно проверять не как отдельную косметику, а как системное свойство

Для этого проекта безопасность не должна откладываться "на потом".

Нужно регулярно проверять:

- auth;
- registration;
- tenant-aware выборки;
- role-based доступ;
- любые raw query;
- любые публичные поля, которые могут быть выведены в UI позже.

## 10. Подготовка backend к мобильному приложению

Чтобы backend потом безболезненно использовался мобильным приложением, уже сейчас нужно:

- держать API независимым от веб-страниц;
- придерживаться стабильных DTO;
- использовать единый формат ответов и ошибок;
- документировать endpoints через Swagger;
- не переносить бизнес-логику на frontend.

| Каркас backend + тестовая среда | 2-3 дня |

## 12. Вывод

Backend для этого проекта нужно строить не просто как набор endpoint, а как устойчивую SaaS-платформу с четкой tenant-изоляцией, role-based доступом и предсказуемой бизнес-логикой.

Лучший путь разработки:

- сначала каркас;
- потом тестовая база;
- затем auth и multi-tenant;
- потом menu и orders;
- на каждом этапе сначала тесты, потом код.

Такой подход даст более надежный результат, снизит риск архитектурных ошибок и упростит дальнейшее развитие продукта.
