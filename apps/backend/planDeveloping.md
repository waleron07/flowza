# План разработки backend (TDD)

## 1. Цель backend части

Backend должен стать единым надежным API для SaaS-приложения заказов еды.

Он должен решать следующие задачи:

- аутентификация и авторизация пользователей;
- изоляция данных по tenant;
- управление меню;
- прием и обработка заказов;
- предоставление API для веб-клиента, админки и будущего мобильного приложения.

Разработка backend ведется по подходу **TDD**: сначала описывается структура и поведение через тесты, затем пишется минимальная реализация, затем код рефакторится.

## 2. Подход к разработке: TDD

Основной цикл работы по каждой функции:

1. определить контракт и поведение;
2. написать тест;
3. запустить тест и убедиться, что он падает;
4. написать минимальный код, чтобы тест прошел;
5. выполнить рефакторинг;
6. добавить дополнительные тесты на ошибки и крайние сценарии.

Это нужно, чтобы:

- рано фиксировать бизнес-правила;
- не размывать архитектуру;
- безопасно развивать multi-tenant логику;
- упростить будущую поддержку и подключение мобильного клиента.

## 3. Общая архитектурная стратегия backend

### 3.1. Основные требования

Backend должен быть:

- модульным;
- предсказуемым по контрактам;
- покрытым тестами на критичные сценарии;
- готовым к multi-tenant;
- независимым от конкретного frontend.

### 3.2. Рекомендуемая структура проекта

```text
src/
  main.ts
  app.module.ts
  config/
  common/
    guards/
    decorators/
    filters/

  users/

    users.controller.ts

    tenants.module.ts
    tenants.service.ts
    tests/
  categories/
  products/
  orders/
  health/
test/
  integration/
  e2e/
```

### 3.3. Архитектурные принципы

- бизнес-логика должна жить в сервисах;
- контроллеры должны быть тонкими;
- DTO используются для входных данных;
- вся проверка ролей и tenant выполняется на backend;
- каждый модуль тестируется отдельно;
- общие механизмы выносятся в `common/`.

## 4. Стратегия тестирования

TDD будет эффективным только если заранее разделить тесты по уровням.

### 4.1. Unit tests

Покрывают:

- сервисы;
- бизнес-правила;
- статусы заказов;
- проверки ролей;
- проверки tenant-логики;
- вспомогательные функции и policy-слой.

Цель:

- максимально быстро проверять логику без БД и HTTP.

### 4.2. Integration tests

Покрывают:

- работу сервисов с БД;
- ORM и репозитории;
- реальные запросы к сущностям;
- корректность tenant-фильтрации;
- работу модулей в связке.

Цель:

- убедиться, что код реально работает с базой и не ломается на уровне persistence.

### 4.3. E2E tests

Покрывают:

- login;
- создание заказа;
- просмотр заказов;
- смену статуса заказа;
- запрет доступа при неверной роли;
- запрет доступа к чужому tenant.

Цель:

- проверить реальные пользовательские сценарии через HTTP API.

### 4.4. Язык тестовых кейсов

- все названия тестов (`describe`, `it`) обязательно писать на кириллице;
- формулировки тестов должны описывать поведение понятным русским языком;
- англоязычные названия допускаются только для технических терминов API/протоколов (`JWT`, `HTTP`, `DTO`).

## 5. Что тестировать в первую очередь

Самые критичные зоны backend:

1. аутентификация;
2. роли и доступы;
3. multi-tenant изоляция;
4. создание заказа;
5. переходы статусов заказа.

Если тестов мало, начинать нужно именно с этих зон.

## 5.1. Уточненные требования к пользователям и ролям

Ниже зафиксированы продуктовые правила перед началом Этапа 1.

### Актуализация auth-контракта (обязательно к реализации)

- поле `firstName` в модели `User` заменено на `login`;
- `login` обязателен для всех ролей и должен быть уникальным;
- `email` обязателен для всех ролей и должен быть уникальным;
- поле `lastName` удалено и не используется в продукте;
- регистрация клиента (`user`) требует: `login`, `email`, `phone`, `password`, согласие с политикой;
- авторизация выполняется через единое поле `identifier` + `password`;
- в `identifier` разрешены:
  - `email`
  - `phone` (формат `+79XXXXXXXXX`)
  - `login`
- endpoint `POST /auth/login` должен принимать `identifier`, а не `phone`.

### Регистрация клиента (`user`)

- пользователь-клиент регистрируется самостоятельно;
- перед завершением регистрации пользователь обязан согласиться с политикой конфиденциальности;
- в MVP-форме регистрации обязательны 3 поля:
  - `phone` (только российский номер);
  - `email` (валидный email);
  - `login`.

### CAPTCHA (бесплатная) и согласие на обработку ПДн (РФ)

- для защиты регистрации от ботов добавляется бесплатная CAPTCHA;
- для MVP зафиксирован и реализован **`Cloudflare Turnstile`** (free): серверная проверка в `TurnstileCaptchaService`, секрет `TURNSTILE_SECRET_KEY`; тестовые ключи Cloudflare возвращают токен `XXXX.DUMMY.TOKEN.XXXX` (на фронте явно допускается как валидный клиентский токен);
- backend не доверяет frontend и всегда валидирует captcha-токен через серверную проверку у провайдера CAPTCHA;
- регистрация без валидного captcha-токена отклоняется;
- на странице регистрации пользователь должен явно подтвердить согласие с документом
  `Согласие на обработку персональных данных` (в соответствии с 152-ФЗ);
- checkbox согласия обязателен, значение должно быть `true`, иначе регистрация отклоняется;
- документ согласия должен иметь постоянную ссылку и версию (например, `agreementVersion`), чтобы можно было зафиксировать,
  с какой редакцией пользователь согласился.

### Верификация email-кодом при регистрации

**Статус:** локальный сценарий верификации по email **подтвержден в эксплуатации для development-окружения**: исходящие письма отправляются через рабочий SMTP (`Gmail SMTP` + пароль приложения), а тестовая отправка и авторизация по SMTP уже успешно проверены. Для production это не отменяет отдельной проверки env и доставки на целевом окружении, но сценарий «получил код на почту → ввёл код» больше не считается заблокированным на этапе локальной разработки.

- регистрация клиента должна подтверждаться одноразовым кодом, отправленным на email;
- без подтверждения кода аккаунт не переводится в активное состояние;
- код должен иметь ограниченный срок жизни (например, 10-15 минут);
- должен быть отдельный сценарий повторной отправки кода с ограничением частоты запросов;
- после успешной верификации код помечается использованным и не может применяться повторно.

#### Этап 2. API-контракт регистрации

1. `POST /auth/register`
   - принимает `phone`, `email`, `login`, `password`, `consentToPrivacyPolicy`, `consentToPersonalData`, `captchaToken`;
   - создает пользователя в статусе "не подтвержден";
   - генерирует код и отправляет его на email;
   - возвращает технический результат без авторизации.
2. `POST /auth/register/verify-email`
   - принимает `email` (или `userId`) и `code`;
   - проверяет срок и валидность кода;
   - помечает email как подтвержденный;
   - выдает JWT (или разрешает login, в зависимости от выбранного flow).
3. `POST /auth/register/resend-email-code`
   - принимает `email`;
   - повторно отправляет код при соблюдении rate limit;
   - возвращает нейтральный ответ без утечки информации о существовании аккаунта.

##### Детализация DTO и ответов API

1. `POST /auth/register`

Request body:

- `phone: string` (обязательно, формат `+79XXXXXXXXX`);
- `email: string` (обязательно, валидный email);
- `login: string` (обязательно, 3-40 символов);
- `password: string` (обязательно, минимальная длина 8);
- `consentToPrivacyPolicy: boolean` (обязательно, только `true`).
- `consentToPersonalData: boolean` (обязательно, только `true`);
- `agreementVersion: string` (обязательно, версия документа согласия, например `2026-04-04`);
- `captchaToken: string` (обязательно, токен от CAPTCHA-провайдера).

Response `201 Created`:

- `success: true`
- `message: "Код подтверждения отправлен на email"`
- `verificationRequired: true`
- `verificationTtlSec: number` (например, `900`)
- `resendAvailableInSec: number` (например, `60`)

Ошибки:

- `400 Bad Request`:
  - невалидный `phone`
  - невалидный `email`
  - `consentToPrivacyPolicy != true`
  - `consentToPersonalData != true`
  - отсутствует `agreementVersion`
  - отсутствует `captchaToken`
- `401 Unauthorized`:
  - CAPTCHA-токен невалиден или просрочен
- `409 Conflict`:
  - `phone` уже используется
  - `email` уже используется
- `429 Too Many Requests`:
  - превышен лимит регистрации с IP/email.

2. `POST /auth/register/verify-email`

Request body:

- `email: string` (обязательно);
- `code: string` (обязательно, например 6 цифр).

Response `200 OK` (вариант текущего flow с автоавторизацией):

- `success: true`
- `accessToken: string`
- `user: { id, role, phone, email, login, primaryTenantId }`

Response `200 OK` (альтернативный flow без автоавторизации):

- `success: true`
- `verified: true`
- `message: "Email подтвержден, выполните вход"`

Ошибки:

- `400 Bad Request`:
  - неверный формат кода
- `401 Unauthorized`:
  - код неверный или просрочен
- `404 Not Found`:
  - пользователь не найден (опционально лучше вернуть нейтральный `401`)
- `409 Conflict`:
  - email уже подтвержден
- `429 Too Many Requests`:
  - превышен лимит попыток проверки.

3. `POST /auth/register/resend-email-code`

Request body:

- `email: string` (обязательно).

Response `200 OK` (нейтральный):

- `success: true`
- `message: "Если аккаунт существует, код отправлен"`
- `resendAvailableInSec: number`

Ошибки:

- `429 Too Many Requests`:
  - слишком частые запросы resend.

##### Служебные правила контракта

- во всех ответах использовать единый формат `success/message/errorCode/details`;
- не раскрывать, существует ли конкретный `email`, в публичных ответах resend;
- `errorCode` должен быть стабильным для web-клиента:
  - `AUTH_INVALID_PHONE`
  - `AUTH_INVALID_EMAIL`
  - `AUTH_EMAIL_ALREADY_USED`
  - `AUTH_PHONE_ALREADY_USED`
  - `AUTH_CAPTCHA_REQUIRED`
  - `AUTH_CAPTCHA_INVALID`
  - `AUTH_PERSONAL_DATA_CONSENT_REQUIRED`
  - `AUTH_VERIFICATION_CODE_INVALID`
  - `AUTH_VERIFICATION_CODE_EXPIRED`
  - `AUTH_RATE_LIMITED`;
- верификация должна быть идемпотентной: повторный запрос для уже подтвержденного email возвращает предсказуемый результат (`verified: true` или `409` по принятому правилу).

#### Этап 3. Сервис отправки email

1. Ввести абстракцию `EmailSender` (интерфейс + провайдер).
2. Сделать адаптер для SMTP/провайдера транзакционных писем.
3. Шаблон письма:
   - короткий одноразовый код;
   - срок действия;
   - предупреждение "если это не вы, игнорируйте письмо".
4. Все SMTP-настройки вынести в `env`:
   - `SMTP_HOST`, `SMTP_PORT`, `SMTP_USER`, `SMTP_PASS`, `SMTP_FROM`.

Статус реализации:

- выполнено: отправка кода подключена через SMTP (`nodemailer`) в `EmailSenderService`;
- выполнено: тема и текст письма вынесены в отдельный шаблонизатор `EmailTemplateService` (поддерживаются `text` и `html`);
- выполнено: SMTP-переменные добавлены в `apps/backend/.env*`:
  - `SMTP_HOST`, `SMTP_PORT`, `SMTP_SECURE`, `SMTP_USER`, `SMTP_PASS`, `SMTP_FROM`;
  - `SMTP_RETRY_COUNT`, `SMTP_RETRY_DELAY_MS`;
  - `SMTP_CONNECTION_TIMEOUT_MS`, `SMTP_GREETING_TIMEOUT_MS`, `SMTP_SOCKET_TIMEOUT_MS`;
- выполнено: загрузка env через `ConfigModule` настроена для локального запуска backend;
- выполнено: в ответах `POST /auth/register` и `POST /auth/register/resend-email-code` добавлено поле **`emailSentViaSmtp`** (`true` только если письмо реально ушло через SMTP; `false` — код в логах сервера из‑за незаполненного SMTP);
- выполнено: при ошибке SMTP в лог пишутся `responseCode` / `response` / `EAUTH`; для 535/аутентификации API возвращает понятное сообщение (проверить логин/пароль, пароль приложения Яндекса при 2FA);
- выполнено: в development-окружении подтверждена реальная отправка письма через `smtp.gmail.com:465` с паролем приложения Google;
- поведение для dev/test:
  - при незаполненном SMTP код логируется в backend (fallback для локальной разработки);
  - при заполненном SMTP код отправляется на реальный email (при успешной аутентификации на SMTP-сервере).

#### Этап 4. Безопасность и анти-абьюз

1. Ограничить частоту:
   - на `register`;
   - на `verify-email`;
   - на `resend-email-code`.

2. Код хранить только в виде хеша, а не в открытом виде.
3. Сравнение кода делать безопасным способом (без утечек по таймингу).
4. После успешного подтверждения:
   - инвалидировать все активные коды пользователя;
   - запретить повторное использование кода.
5. Логировать события безопасности:
   - частые неуспешные попытки;
   - массовые resend-запросы;
   - попытки проверки просроченных кодов.

#### Этап 5. Тесты

1. Unit:
   - генерация/хеширование/проверка кода;
   - проверка TTL;
   - проверка блокировок по лимитам.
2. Integration:
   - полный цикл `register -> verify-email`;
   - повторная отправка кода;
   - отказ по неверному/просроченному коду.
3. E2E:
   - успешная регистрация с подтверждением email;
   - невозможность логина/получения полного доступа без подтверждения email;
   - проверка повторного использования старого кода (должен быть отказ).

#### Этап 6. Definition of Done

- клиент не может завершить регистрацию без `email`;
- клиент не может завершить регистрацию без валидного `captchaToken`;
- клиент не может завершить регистрацию без `consentToPersonalData = true`;
- клиент не может активировать аккаунт без подтверждения email-кода;
- подтвержденный аккаунт получает ожидаемый auth-flow;
- повторная отправка кода и rate limit работают стабильно;
- сценарии покрыты unit/integration/e2e тестами и проходят в CI.

### Ролевая модель и права создания пользователей

Используемые роли:

- `superAdmin`
- `admin`
- `moderator`
- `operator`
- `user` (клиент приложения)

Общие правила по ролям:

- `superAdmin` имеет полный доступ ко всем организациям и ко всем административным операциям платформы;
- `admin`, `moderator` и `operator` могут быть привязаны не к одной, а к нескольким организациям;
- `superAdmin` логически имеет доступ ко всем организациям, даже если явная привязка к конкретной организации не хранится как обычная staff-связь;
- `user` остается клиентской ролью и не участвует в staff-матрице прав админки.

Правила создания пользователей через админку:

- `operator` и `moderator` может создать только `admin` или `superAdmin`;
- `admin` может создавать только `moderator` и `operator`;
- `superAdmin` может создавать `admin`, `moderator` и `operator`;
- роль `superAdmin` не создается обычными админскими операциями (задается вручную/seed/закрытым процессом);
- роль `user` создается через публичную регистрацию клиента.

Правила управления staff-пользователями через админку:

- `superAdmin` может создавать всех пользователей staff-части и управлять всеми ролями;
- `admin` может создавать `moderator` и `operator`;
- `admin` и `superAdmin` могут редактировать роли `moderator` и `operator`;
- `admin` и `superAdmin` могут удалять `moderator` и `operator`;
- `moderator` и `operator` не могут управлять staff-пользователями;
- операции создания, редактирования и удаления staff-пользователей всегда должны проверяться по роли инициатора и по доступным ему организациям.

### Единая таблица пользователей

Все пользователи хранятся в одной таблице `users`.

Поля таблицы:

- `id` — уникальный идентификатор;
- `primaryTenantId` — primary tenant пользователя для совместимости и явной бизнес-семантики, но не единственный источник multi-tenant доступа;
- `avatar` — аватар пользователя через отдельную модель изображения;
- `email` — обязателен для роли `user` (для staff-ролей может оставаться опциональным);
- `phone` — обязательно, только РФ формат;
- `role` — роль пользователя (`superAdmin | admin | moderator | operator | user`);
- `login` — обязательно, уникально;
- `isActive` — boolean;
- `createdAt`, `updatedAt`.

### Уточнение по SaaS-модели организаций

Новый продуктовый контекст требует скорректировать трактовку tenant-модели.

Важно:

- в системе будет список организаций;
- у каждой организации своя инфраструктура данных:
  - категории
  - продукты
  - цены
  - заказы
- пользователь-клиент должен видеть список организаций и иметь возможность сделать заказ в каждой из них;
- staff-пользователи (`admin`, `moderator`, `operator`) могут быть привязаны сразу к нескольким организациям;
- `superAdmin` работает над платформой в целом и имеет доступ ко всем организациям.

Из этого следует важное архитектурное правило:

- поле `primaryTenantId` у `users` нельзя трактовать как единственный источник доступа ко всем ролям и всем организациям;
- для staff-пользователей связь с tenant остается обязательной по бизнес-смыслу, но должна поддерживать множественную привязку;
- для клиентского пользователя `user` нельзя жестко фиксировать единственный tenant как постоянную принадлежность ко всей системе;
- принадлежность клиента к организации должна определяться не самим пользователем как сущностью платформы, а его действиями в контексте конкретной организации:
  - просмотр меню tenant
  - создание заказа tenant
  - история заказов по tenant

Практический вывод для следующего шага:

- текущего поля `primaryTenantId` у `User` недостаточно для целевой staff-модели;
- для `admin`, `moderator` и `operator` нужна отдельная модель множественной привязки к организациям;
- `superAdmin` должен обрабатываться как глобальная роль с доступом ко всем организациям;
- изображения tenant, категорий, продуктов и аватар пользователя должны храниться через отдельную модель `Image`;
- tenant-контекст для клиента должен входить в заказы и публичные каталоги организаций;
- заказы клиента должны быть привязаны к организации (`tenant`), а не вся клиентская учетная запись целиком к одной организации.

### Правила управления организациями

- организацию может создавать только `superAdmin`;
- организацию может редактировать только `superAdmin` или `admin`;
- организацию может удалять только `superAdmin`;
- у организации должно быть поле `subscription: Date`, которое показывает, до какой даты действует подписка;
- поле `isActive` у организации может редактировать только `superAdmin`;
- поле `subscription` у организации может редактировать только `superAdmin`;
- `admin` может управлять только теми организациями, к которым он привязан;
- `moderator` и `operator` не могут создавать, редактировать или удалять организации.

### Матрица прав по ролям

#### `superAdmin`

- имеет полный доступ ко всем организациям;
- может создавать, редактировать и удалять организации;
- может изменять `isActive` и `subscription` у организаций;
- может создавать всех staff-пользователей;
- может редактировать и удалять staff-пользователей;
- может выполнять любые административные действия платформы.

#### `admin`

- может работать только в рамках привязанных к нему организаций;
- может редактировать организацию в пределах доступных ему организаций;
- не может изменять `isActive` и `subscription` у организаций;
- может создавать `moderator` и `operator`;
- может редактировать и удалять `moderator` и `operator` в пределах доступных организаций;
- может наполнять организацию данными;
- может создавать, редактировать и удалять категории;
- может создавать, редактировать и удалять карточки товаров;
- может выполнять прочие административные действия, связанные с управлением своей организацией.

#### `moderator`

- может работать только в рамках привязанных к нему организаций;
- может наполнять карточки товаров;
- может создавать, редактировать и удалять карточки товаров;
- может создавать, редактировать и удалять категории;
- не может управлять организациями;
- не может управлять staff-пользователями.

#### `operator`

- может работать только в рамках привязанных к нему организаций;
- может входить в админку;
- может просматривать заказы;
- может менять статусы заказов;
- может писать комментарии к заказам;
- не может управлять организациями;
- не может управлять staff-пользователями;
- не может наполнять каталог на уровне категорий и карточек товаров.

### Этап 7.1. Security hardening backend

**Оценка:** 2-4 дня

**Прогресс:** в работе | **Блокер:** нет | **Обновлено:** 2026-04-29

Этот этап становится следующим обязательным шагом параллельно развитию multi-tenant модели.

#### Что проверить в первую очередь

- устойчивость auth и registration к вредоносному вводу;
- устойчивость DTO и сервисов к script injection payload;
- устойчивость слоя доступа к данным к SQL injection;
- корректность authorization по ролям;
- корректность tenant-изоляции при доступе к данным;
- отсутствие небезопасных raw SQL вызовов без параметризации;
- устойчивость публичных endpoint к brute force и бот-активности.

#### Ключевые риски

- script injection через названия организаций, категорий, продуктов или профильные поля;
- SQL injection через raw query или небезопасную динамическую фильтрацию;
- обход authorization через неправильную проверку роли или tenant;
- массовые запросы на `register` и `login`;
- утечка данных между организациями;
- доверие только frontend-валидации без жесткой backend-проверки.

#### Сначала описать тестами

- вредоносные строки в DTO не ломают обработку и не обходят валидацию;
- SQL injection payload не влияет на выборку данных;
- запрос без нужной роли получает отказ;
- запрос с tenant A не может получить данные tenant B;
- login не выдает лишней информации о существовании пользователя;
- registration корректно обрабатывает повторные и вредоносные запросы;
- protected endpoint недоступен без валидного токена;
- raw SQL, если появится, используется только параметризованно.

#### После тестов реализовать

- review всех публичных auth endpoint;
- review всех мест с динамическими фильтрами и будущими raw query;
- защиту от script injection на уровне DTO/сервисов/хранимых данных;
- rate limiting для публичных auth endpoint;
- anti-bruteforce подход для `login`;
- централизованный security checklist для новых модулей;
- подготовку точки интеграции для captcha в будущем.

#### Что добавить позже

- captcha для `register`;
- captcha или adaptive challenge для `login`;
- audit log для auth-событий;
- расширенные security e2e сценарии;
- review refresh/session стратегии, если auth-схема будет расширяться.

#### Результат этапа

## 9. Что важно не упустить при TDD

### 9.1. Не тестировать framework вместо логики

Не нужно тратить много времени на тесты очевидного поведения NestJS.
Нужно тестировать именно свою бизнес-логику:

- кто что может делать;
- какие данные видит пользователь;
- какие статусы допустимы;
- что запрещено между tenant.

### 9.2. Не писать слишком много хрупких тестов на внутреннюю реализацию

Лучше проверять:

- поведение;
- входные данные;
- итоговый результат;
- побочные эффекты в БД.

И хуже проверять:

- сколько раз вызван приватный метод;
- внутреннюю структуру сервиса без бизнес-смысла.

### 9.3. Multi-tenant должен проверяться почти в каждом модуле

Для этого проекта tenant-контекст — это не частная деталь, а фундамент архитектуры.
Поэтому тесты tenant-изоляции должны присутствовать во всех ключевых модулях.

### 9.4. Security нужно проверять не как отдельную косметику, а как системное свойство

Для этого проекта безопасность не должна откладываться "на потом".

Нужно регулярно проверять:

- auth;
- registration;
- tenant-aware выборки;
- role-based доступ;
- любые raw query;
- любые публичные поля, которые могут быть выведены в UI позже.

Лучший путь разработки:

- сначала каркас;
- потом тестовая база;

Такой подход даст более надежный результат, снизит риск архитектурных ошибок и упростит дальнейшее развитие продукта.
