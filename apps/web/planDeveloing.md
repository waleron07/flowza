# План разработки web frontend (TDD)

## 1. Цель web части

`apps/web` — это клиентская часть Flowza для конечного пользователя.

Web frontend должен решать следующие задачи:

- вход в приложение без обязательной авторизации;
- выбор организации перед оформлением заказа;
- регистрация клиента;
- login клиента;
- просмотр меню;
- работа с корзиной;
- оформление заказа;
- просмотр своих заказов;
- в дальнейшем: профиль клиента, история заказов, дополнительные сценарии лояльности.

Разработка ведется по **TDD-подходу**:

1. сначала описывается поведение экрана и пользовательский сценарий;
2. затем пишется тест;
3. затем реализуется минимальный рабочий код;
4. после прохождения тестов выполняется рефакторинг.

## 2. Зависимость от backend

Web frontend будет строиться поверх backend API.

### Актуализация auth-контракта (синхронизация с backend)

- поле `firstName` заменено на `login`;
- поле `lastName` удалено и не используется;
- в регистрации обязательны: `login`, `email`, `phone`, `password`, согласие с политикой;
- `email` обязателен для всех пользователей;
- вход выполняется через:
  - `identifier`
  - `password`
- `identifier` может быть:
  - `email`
  - `phone`
  - `login`
- все UI-состояния/типы web, где использовался `firstName`, нужно перевести на `login`.

### CAPTCHA и согласие на обработку персональных данных (РФ)

- в форме регистрации используется **`Cloudflare Turnstile`** (`@marsidev/react-turnstile`, ключ `VITE_TURNSTILE_SITE_KEY`); тестовые ключи Cloudflare отдают токен `XXXX.DUMMY.TOKEN.XXXX` — на фронте он учитывается как валидный; без ключа в dev возможен fallback-чекбокс с `CAPTCHA_MOCK_VALID_TOKEN` на backend;
- token CAPTCHA обязателен и отправляется в backend как `captchaToken`;
- на форме регистрации обязателен checkbox:
  - `Я согласен(на) с обработкой персональных данных`;
- рядом с checkbox должна быть ссылка на документ:
  - `Согласие на обработку персональных данных` (публичная страница/документ);
- frontend отправляет в backend:
  - `consentToPersonalData: true`
  - `agreementVersion` (версия документа, показанного пользователю);
- если checkbox не отмечен, submit блокируется на frontend;
- если backend вернул ошибку по CAPTCHA/согласию, UI показывает отдельное понятное сообщение.

На текущий момент backend уже не является абстрактной заготовкой, а дает рабочую основу для пользовательского auth-сценария и локальной разработки:

- поднят `NestJS` backend внутри `apps/backend`;
- подключены `PostgreSQL` и `Prisma`;
- база запускается локально, миграции уже применяются через Prisma;
- backend доступен локально на `http://localhost:3001`;
- включен `CORS` для локальных frontend-приложений:
  - `http://localhost:5173` для `admin`
  - `http://localhost:5174` для `web`

Для пользовательской части уже доступны endpoint:

- `POST /auth/register` (ответ может содержать `emailSentViaSmtp`: `false`, если письмо не ушло по SMTP — код тогда в логах бэкенда)
- `POST /auth/register/verify-email`
- `POST /auth/register/resend-email-code`
- `POST /auth/login`
- `GET /auth/me`
- `DELETE /auth/me`

Также на backend уже появился отдельный staff-сценарий для админки:

- `POST /users/staff`

Но этот endpoint относится только к `admin` и не должен использоваться в `web`.

При этом на backend уже зафиксирована tenant-aware доменная модель для будущих пользовательских сценариев:

- `Tenant` с `timezone`, `workingHours`, `deliveryFee`, `minOrderAmount`;
- tenant-scoped `Cart` с правилом `один пользователь + одна организация`;
- tenant-aware `Order` с `orderNumber`, breakdown цены и snapshot-полями;
- `PromoCode` и `Discount` как отдельные сущности скидок;
- `Address` и snapshot адреса в заказе.

Вывод для `apps/web`:

- сейчас можно начинать `guest-first` сценарий поверх уже готового auth backend;
- web должен использовать только клиентские auth-endpoint;
- меню, корзину и заказы стоит брать в активную разработку после появления соответствующих публичных backend-контрактов;
- tenant-aware UX уже нужно проектировать под реальную backend-схему, а не под временные mock-упрощения.

### Синхронизация с реализацией (2026-04-04)

- Регистрация: многошаговый flow (форма → код из письма → успех), **Cloudflare Turnstile**, валидация вынесена в схему; на шаге кода учитывается **`emailSentViaSmtp`** (предупреждение, если письмо не ушло по SMTP).
- Сообщения об ошибках API: `getApiErrorMessage` и восстановление кириллицы при «кракозябрах» в теле ответа (`fixApiMessageMojibake`).
- Auth-страницы: ссылка «войти как гость», страница согласия на обработку ПДн по постоянному маршруту.

## 2.1. Следующий архитектурный шаг: организации и tenant-модель на web

Следующий крупный шаг для `apps/web` — перестроить клиентскую часть не просто вокруг одного общего меню, а вокруг списка организаций.

Бизнес-смысл:

- в системе будет несколько организаций;
- у каждой организации своя инфраструктура данных:
  - категории
  - меню
  - цены
  - в будущем возможно свои настройки доставки, график работы и промо-механики
- один и тот же пользователь должен иметь возможность открыть разные организации и оформить заказ в каждой из них.

Вывод для архитектуры `web`:

- меню нельзя считать глобальным;
- категории нельзя считать глобальными;
- цены нельзя считать глобальными;
- выбранная организация должна стать частью клиентского контекста приложения;
- все запросы меню/категорий/заказов должны быть привязаны к выбранной организации;
- корзина тоже должна быть tenant-aware на уровне frontend.

Критически важное правило:

- нельзя смешивать товары разных организаций в одной корзине без явной бизнес-логики;
- безопасный базовый вариант для MVP: одна корзина на одну организацию;
- при переключении организации frontend должен либо:
  - показывать отдельную корзину этой организации
  - либо явно предупреждать, что текущая корзина относится к другой организации

Это нужно зафиксировать до активной разработки реального меню и checkout, иначе потом придется переделывать почти весь пользовательский flow.

## 4. UI и стилизация

### Дизайн-система

Для `apps/admin` уже принят подход с `MUI`, `theme` и `styles.ts`.

Для `apps/web` это тоже должно стать целевым стандартом после подключения `MUI`.

Это означает:

- все базовые UI-компоненты строятся на `@mui/material`;
- формы, кнопки, карточки, контейнеры и диалоги опираются на `MUI`;
- кастомизация внешнего вида идет через единый `theme`.

### Подход к стилям

Стилизация в `apps/web` также должна строиться через `theme` и `sx`.

Основные правила:

- прикладной UI не должен опираться на разрозненные `.css` файлы;
- стили конкретного компонента выносятся в `styles.ts`;
- компонент использует `sx`-объекты из `styles.ts`;
- цвета, отступы, размеры и типографика контролируются через theme-подход.

### Рекомендуемый паттерн компонентов

```text
ComponentName/
  index.tsx
  styles.ts
```

Где:

- `index.tsx` содержит логику, разметку и привязку событий;
- `styles.ts` содержит объект `sx` для `MUI`.

Именно этот стиль реализации считается целевым и для `apps/web`.

## 5. Основные принципы web frontend

- бизнес-логика остается на backend;
- web frontend отвечает за UX и взаимодействие пользователя;
- пользователь должен иметь возможность войти в web как `Guest` без авторизации;
- `Guest` может просматривать меню и собирать корзину так же, как авторизованный клиент;
- авторизация обязательна не на входе в приложение, а в точке оформления заказа;
- если `Guest` нажимает оформить заказ, frontend показывает модальное окно с предложением:
  - войти
  - зарегистрироваться
- форма регистрации клиента должна включать не только `phone`, но и `email` как обязательное поле;
- форма регистрации должна включать CAPTCHA и обязательное согласие с документом по персональным данным (РФ);
- завершение регистрации должно подтверждаться кодом из email (шаг ввода кода подтверждения); реальная доставка письма зависит от настроенного SMTP на backend (при `emailSentViaSmtp === false` UI показывает предупреждение и отсылает к логам сервера);
- после login или registration корзина не очищается и пользователь продолжает сценарий checkout;
- роль `Guest` на web-слое является frontend-состоянием ограниченного доступа, а не отдельной записью в БД;
- выбранная организация должна быть частью глобального состояния приложения;
- UI должен явно показывать, с какой организацией сейчас работает пользователь;
- данные разных организаций не должны визуально и логически смешиваться;
- корзина, checkout и история заказов должны быть привязаны к текущей организации;
- безопасность пользовательского ввода должна учитываться уже на web-слое, даже если основная защита остается на backend;
- для страницы регистрации обязательно поддерживать состояния CAPTCHA:
  - `initial`
  - `token-ready`
  - `expired`
  - `error/retry`;
- каждая фича должна иметь:
  - `loading`
  - `error`
  - `empty-state`
- тесты описываются на кириллице;
- интерфейс строится модульно;
- структура должна быть готова к масштабированию и мобильному приложению в будущем.

### Подход к роутингу по ролям

Для `apps/web` принимается подход с раздельным роутингом по frontend-ролям, похожий на схему со скрина:

- `Guest` router
- `User` router
- при необходимости позже можно добавить другие role-router уровни без переписывания общего входа

Зачем это нужно:

- проще изолировать возможности гостя и авторизованного клиента;
- легче расширять функциональность по ролям;
- меньше условной логики внутри одного большого роутера;
- проще отдельно развивать checkout-gate для `Guest` и полноценные пользовательские сценарии для `User`.

## 7. MVP web

### Что должно быть в MVP

- вход в приложение как `Guest` без авторизации;
- список организаций;
- выбор активной организации;
- регистрация клиента;
- login клиента;
- базовый профиль;
- меню доступно гостю и авторизованному клиенту в контексте выбранной организации;
- удаление собственного аккаунта;
- корзина в контексте выбранной организации;
- checkout требует авторизации;
- модальное окно авторизации/регистрации при попытке checkout от `Guest`;
- сохранение корзины после login/register;
- история своих заказов.

### Что пока не входит в первый web MVP

- сложная персонализация;
- избранное;
- отзывы;
- бонусы и промокоды;
- push/email уведомления;
- сложный профиль с настройками.

### Этап 1. Auth клиента

**Оценка:** 2-4 дня

Это текущий главный приоритет для `apps/web`, но уже в `guest-first` формате: вход в приложение не должен требовать обязательного login, а auth должен включаться по требованию пользователя и в точке checkout.

#### Сначала описать тестами

- гость попадает в приложение без авторизации;
- успешная регистрация клиента;
- ошибка регистрации без валидных данных;
- ошибка регистрации без `email`;
- отправка и успешная проверка email-кода подтверждения;
- ошибка подтверждения при неверном/просроченном коде;
- успешный login;
- ошибка login при неверных данных;
- переключение видимости пароля по иконке "показать/скрыть пароль";
- на auth-страницах есть переход на страницу регистрации;
- на auth-страницах есть действие "войти как гость";
- сохранение токена;
- восстановление сессии авторизованного клиента;
- logout очищает сессию;
- удаление собственного аккаунта завершает сессию.

#### После тестов реализовать

- guest session слой;
- страницу регистрации;
- страницу login;
- шаг подтверждения регистрации по email-коду;
- auth/session слой;
- разделение роутера на `Guest` и `User`;
- хранение access token;
- UI-контрол для полей пароля с иконкой "показать пароль";
- ссылки на auth-страницах:
  - переход на регистрацию (для login-экрана);
  - переход на login (для register-экрана);
  - действие "войти как гость";
- восстановление сессии через `GET /auth/me`;
- интеграцию с:
  - `POST /auth/register`
  - `POST /auth/register/verify-email`
  - `POST /auth/register/resend-email-code`
  - `POST /auth/login`
  - `GET /auth/me`
  - `DELETE /auth/me`

#### Детализация web-flow и обработки backend-контракта

1. Шаг `register`:
   - пользователь заполняет `login`, `phone`, `email`, `password`, согласия и CAPTCHA, подтверждает политику;
   - frontend валидирует поля до отправки;
   - при успешном `POST /auth/register` открывается экран ввода кода (flow: форма → **подтверждение email** → при необходимости экран успеха с редиректом);
   - в UI показывать таймер срока действия кода (`verificationTtlSec`) и таймер до resend (`resendAvailableInSec`);
   - учитывать `emailSentViaSmtp` из ответа: при `false` — предупреждение, что письмо не отправлялось по SMTP.
2. Шаг `verify email code`:
   - пользователь вводит код из письма;
   - frontend вызывает `POST /auth/register/verify-email`;
   - при успешном ответе:
     - если вернулся `accessToken`, сразу авторизовать пользователя;
     - если токен не возвращается, перевести на `login` с сообщением "Email подтвержден".
3. Шаг `resend code`:
   - кнопка "Отправить код повторно" активна только после таймера;
   - по клику вызывать `POST /auth/register/resend-email-code`;
   - в UI всегда нейтральное сообщение без раскрытия существования email.
4. Поле пароля:
   - добавить иконку справа в поле (`show/hide password`);
   - состояние видимости хранить локально в компоненте формы;
   - иконка должна быть доступна с клавиатуры и иметь понятный `aria-label`.
5. Навигационные ссылки на auth-страницах:
   - на `login`: ссылка "Нет аккаунта? Зарегистрироваться";
   - на `register`: ссылка "Уже есть аккаунт? Войти";
   - на обеих страницах: действие "Войти как гость";
   - при наличии `redirectTo` сохранять его при переходах между `login/register`.

#### Маппинг `errorCode` -> пользовательский текст

- `AUTH_INVALID_PHONE` -> "Проверьте номер телефона в формате +79XXXXXXXXX";
- `AUTH_INVALID_EMAIL` -> "Введите корректный email";
- `AUTH_EMAIL_ALREADY_USED` -> "Этот email уже используется";
- `AUTH_PHONE_ALREADY_USED` -> "Этот номер уже используется";
- `AUTH_VERIFICATION_CODE_INVALID` -> "Неверный код подтверждения";
- `AUTH_VERIFICATION_CODE_EXPIRED` -> "Код истек, запросите новый";
- `AUTH_RATE_LIMITED` -> "Слишком много попыток, попробуйте позже".

#### UX-состояния, обязательные для auth-экранов

- `loading`: блокировка повторного submit + индикатор запроса;
- `error`: текст ошибки под формой и/или под конкретным полем;
- `success`: подтверждение отправки кода/успешной верификации;
- `empty`: изначальное состояние формы без ошибок;
- `cooldown`: визуальный отсчет до доступности resend.

#### Результат этапа

Пользователь может зайти в приложение как `Guest`, а при login/register перейти в состояние `User` без потери клиентского сценария.

### Этап 8. Безопасность web frontend

**Оценка:** 2-4 дня**

Этот этап нужен не как косметика, а как обязательная подготовка к публичному доступу web-клиента.

#### Что проверить в первую очередь

- устойчивость форм `login/register` к некорректному и вредоносному вводу;
- отсутствие небезопасного рендера пользовательских данных;
- корректную обработку текстов, которые потенциально могут содержать скриптовые вставки;
- сценарии авторизации и восстановления сессии;
- сценарии регистрации и повторных запросов;
- поведение при ошибках backend;
- сохранность guest/cart flow при auth-переходах;
- защиту публичных форм от ботов.

#### Ключевые риски

- XSS через отображаемые данные организации, меню, категории или профиля;
- script injection через пользовательский ввод;
- автоматические бот-запросы в `register/login`;
- brute force попытки входа;
- утечки состояния между `Guest` и `User`;
- небезопасное хранение или использование токена;
- доверие frontend-валидации без backend-проверки.

#### Что сделать на web-слое

- не использовать `dangerouslySetInnerHTML` без крайней необходимости;
- считать все строки от backend потенциально недоверенными;
- валидировать формы до отправки;
- централизованно обрабатывать backend-ошибки auth и registration;
- не допускать утечки защищенных экранов в guest-flow;
- предусмотреть точку интеграции для `captcha` в `login/register`;
- подготовить UX для антибот-проверки без ломки текущих форм.

#### Что обязательно должно оставаться на backend

- tenant-изоляция;
- проверка прав доступа;
- rate limiting;
- anti-bruteforce механизмы;
- реальная проверка captcha-token;
- финальная валидация всех входных данных;
- защита от межtenant доступа.

#### Что нужно добавить позже

- `captcha` в `register`;
- `captcha` или adaptive challenge в `login`;
- аудит auth-событий;
- отдельные security-тесты на вредоносные строки и XSS-подобные payload;
- review хранения access token и возможный переход на более безопасную auth-схему.

#### Результат этапа

Web frontend остается удобным для гостя и клиента, но становится заметно устойчивее к вредоносному вводу, ботам и ошибкам в публичных auth-сценариях.

## 11. Итог

`apps/web` нужно развивать как отдельный клиентский интерфейс для пользователя, но уже с учетом нового состояния монорепы:

- backend уже рабочий по auth, БД и локальной интеграции;
- admin уже реализовал первый законченный frontend-сценарий поверх backend;
- web должен унаследовать инженерные решения admin, но применить их к клиентским сценариям.

Практический приоритет для web сейчас такой:

1. добавить тесты на переключение организаций и tenant-aware корзину;
2. провести security-проработку `login/register` и guest-flow;
3. подготовить точку интеграции для `captcha`;
4. дождаться и подключить реальные публичные backend-контракты меню, корзины и checkout;
5. история заказов;
6. затем остальные пользовательские сценарии по мере готовности backend-контрактов.

Целевые правила разработки остаются такими:

- `MUI` как UI-основа;
- стили через `theme` и `sx`;
- TDD;
- модульная структура;
- backend-first контракты.

Это позволит держать единый стиль разработки между `admin` и `web`, но не смешивать сценарии сотрудников и клиентов.
